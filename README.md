# Secret-Vault

Secret-Vault היא תוכנת CLI לשיתוף קבצים מוצפנים. בעל הקובץ בוחר 2–16 משתמשים מורשים וסף אישורים. הקובץ, המפתח הפרטי ושחזור המפתח נשארים בצד הלקוח; השרת מנהל חשבונות, הרשאות וחומר מוצפן.

## איך השיתוף עובד

1. הלקוח מצפין את הקובץ עם AES-256-GCM. השרת מקבל את ה־Nonce ואת הטקסט המוצפן, לא את מפתח AES.
2. הלקוח מחלק את מפתח AES ל־Shares באמצעות Shamir. הסף חייב להיות לפחות 2 ולא גדול ממספר הנמענים.
3. כל Share מוצפן עם RSA-4096 OAEP/SHA-256 למפתח הציבורי של המשתמש שלו.
4. השרת שומר את הקובץ המוצפן ואת ה־Shares המוצפנים.
5. משתמש מורשה יכול להפעיל את האישור שלו. הלקוח שלו מפענח את ה־Share האישי ומצפין אותו בנפרד עבור כל משתמש מורשה.
6. השרת בודק שהלקוח שלח Share מוצפן לכל מורשה בדיוק פעם אחת, שומר את העותקים המוצפנים ומסמן את האישור כפעיל.
7. אין מגבלת זמן לאישור לפני פתיחת הקובץ. כשמספר האישורים מגיע ל־Threshold, הקובץ נפתח.
8. מרגע הפתיחה רק המשתמשים שאישרו יכולים לראות את פרטי הקובץ ולהוריד אותו. לאחר 60 שניות השרת מוחק את הקובץ, ה־Shares וכל המידע הקשור אליו.
9. כל Share שאושר מוצפן למשתמשים המורשים, ופענוח ה־Shares ושחזור מפתח AES נעשים במחשב המשתמש שאישר.

ביטול אישור אפשרי לפני פתיחת הקובץ. לאחר שהקובץ נפתח, רשימת המאשרים נעולה עד למחיקה האוטומטית. משתמש שקיבל קובץ מפוענח יכול לשמור או להעביר אותו.

## התקנה

אפשר להוריד רק את קובצי השרת, רק את קובצי הלקוח, או את שניהם. הפקודות דורשות Git עם תמיכה ב־sparse checkout ו־PowerShell.

### הורדת השרת בלבד

```powershell
git clone --filter=blob:none --no-checkout https://github.com/arielushka/Secret_Vault.git Secret_Vault-server
Set-Location Secret_Vault-server
git sparse-checkout init --no-cone
git sparse-checkout set '/README.md' '/server/**' '/common/**' '/server.crt'
git checkout main
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install argon2-cffi cryptography
```

### הורדת הלקוח בלבד

```powershell
git clone --filter=blob:none --no-checkout https://github.com/arielushka/Secret_Vault.git Secret_Vault-client
Set-Location Secret_Vault-client
git sparse-checkout init --no-cone
git sparse-checkout set '/README.md' '/client/**' '/common/**' '/server.crt'
git checkout main
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install cryptography shamir-mnemonic
```

### הורדת השרת והלקוח יחד

ההורדה המלאה כוללת את קוד השרת והלקוח ואת קובץ בדיקת ההתקנה. מתקינים את כל התלויות יחד:

```powershell
git clone https://github.com/arielushka/Secret_Vault.git Secret_Vault
Set-Location Secret_Vault
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install argon2-cffi cryptography shamir-mnemonic
```

להתקנה נפרדת: בשרת מריצים `python -m pip install argon2-cffi cryptography`; בלקוח מריצים `python -m pip install cryptography shamir-mnemonic`. בהורדה המלאה מתקינים את שלוש החבילות יחד, כפי שמופיע למעלה. אין בפרויקט קובצי `requirements.txt`.

## הפעלה

בטרמינל הראשון הפעילו את השרת:

```powershell
python -m server.server
```

השרת דורש TLS 1.3 ומאזין כברירת מחדל בכל ממשקי הרשת בפורט 5000. במחשב השרת, מתוך תיקיית הפרויקט, יוצרים פעם אחת תעודת TLS ומפתח פרטי. החליפו את `192.168.1.20` בכתובת ה־IPv4 הקבועה או השמורה של מחשב השרת ברשת הפרטית:

```powershell
openssl req -x509 -newkey rsa:2048 -nodes -keyout server.key -out server.crt -days 365 -subj "/CN=192.168.1.20" -addext "subjectAltName=DNS:localhost,IP:127.0.0.1,IP:192.168.1.20"
```

את `server.key` משאירים במחשב השרת בלבד ואין מעלים אותו ל־Git או שולחים ללקוחות. מעבירים לכל לקוח את `server.crt` שנוצר ושומרים אותו בתיקיית הפרויקט; הלקוח משתמש בו כדי לאמת את תעודת השרת. הלקוחות אינם מריצים OpenSSL. יש להעביר את התעודה בערוץ אמין, ולוודא שה־IP שהלקוח יתחבר אליו מופיע ב־SAN של התעודה.

בכל מחשב לקוח, הגדירו את כתובת השרת לפי הכתובת בדוגמה לעיל ואז הפעילו את הלקוח. הגדירו זאת בכל חלון PowerShell שבו מריצים את התוכנה. אפשר לפתוח כמה לקוחות כדי להשתמש בכמה חשבונות:

```powershell
$env:SECRET_VAULT_HOST = "192.168.1.20"
$env:SECRET_VAULT_PORT = "5000"
python -m client.client
```

השרת מקשיב ב־`0.0.0.0:5000` כברירת מחדל. יש לאפשר חיבור נכנס ל־TCP/5000 בחומת האש של מחשב השרת בפרופיל הרשת הפרטית בלבד, ולהתחבר רק מתוך הרשת המהימנה. אין להגדיר העברת פורטים מהאינטרנט.

השרת יוצר את `database/vault.db` ואת תיקיית `server/uploads` בהפעלה/בהעלאה. הרישום יוצר זוג מפתחות RSA-4096 אצל הלקוח ושומר את המפתח הפרטי בקובץ PEM מוגן בסיסמה. סיסמאות החשבון נשמרות בשרת כ־Argon2 hash.

## מבנה הפרויקט

- `client/client.py`: ממשק ה־CLI.
- `client/vault_client.py`: חיבור לשרת, בדיקת מפתחות ופעולות משתמש.
- `client/file_manager.py` ו־`client/crypto/`: הצפנת קבצים, חלוקת Shares ושמירת מפתחות.
- `common/protocol.py`: מסגור הודעות JSON מעל TCP (עד 16 MiB להודעה).
- `server/server.py`, `server/handlers.py`: חיבורים וניתוב בקשות מאומתות.
- `server/file_handler.py`, `server/database.py`: אימות העלאות, קובצי ciphertext ומסד SQLite.
- `test_installation.py`: בדיקת עשן להתקנה מלאה של השרת והלקוח.
- `test_file_lifecycle.py`: בדיקות אישורים, פתיחה, הרשאות ותפוגה.

## אישור מפתחות ציבוריים

בפעם הראשונה שמשתמש מקבל מפתח ציבורי של משתמש אחר, התוכנה מציגה את טביעת האצבע שלו. יש להשוות אותה למידע שקיבלת מהמשתמש בדרך נפרדת ואמינה, למשל שיחה ישירה. רק לאחר אישור היא נשמרת מקומית בקובץ `trusted_keys.json`. אם המפתח משתנה, התוכנה עוצרת ולא מחליפה את האישור השמור.

בהתחברות, הלקוח גם משווה את המפתח הציבורי שהשרת מחזיר למפתח הפרטי המקומי, כדי לוודא שהמפתח של המשתמש עצמו לא הוחלף.

## מפתחות פרטיים

המפתח הפרטי נשמר במחשב המשתמש בקובץ מוצפן בסיסמה, תחת `~/.secret_vault/keys` (ב־Windows: בתיקיית המשתמש). אפשר לבחור תיקייה אחרת בעזרת משתנה הסביבה `SECRET_VAULT_KEY_DIR`. השרת שומר מפתחות ציבוריים בלבד.

## בדיקת התקנה מלאה

הקבצים `test_installation.py` ו־`test_file_lifecycle.py` נמצאים בהורדה המלאה בלבד. הראשון בודק את קובצי שני הצדדים ואת חיבור TLS ביניהם; השני בודק אישורים, פתיחה, הרשאות ומחיקה אחרי 60 שניות.

בדיקת מחזור החיים אינה דורשת שרת פעיל ומשתמשת במסד זמני:

```powershell
python -m unittest test_file_lifecycle -v
```

כדי לבדוק גם את חיבור TLS, התקינו את התלויות, צרו תעודה ומפתח עם OpenSSL והפעילו את השרת. בחלון PowerShell נוסף באותו מחשב הריצו:

```powershell
python -m unittest test_installation -v
```

בדיקת ההתקנה מוודאת שהתלויות וקובצי שני הצדדים זמינים, שהתעודה והמפתח תואמים, יוצרת חיבור TLS 1.3 לשרת המקומי ושולחת בקשת פרוטוקול לא מאומתת כדי לוודא שהשרת מחזיר את שגיאת ההתחברות הנדרשת.

## מגבלות

- השרת מאזין ברשת ב־TCP/5000 ומשתמש ב־TLS 1.3. השימוש מיועד לרשת פרטית מהימנה בלבד; יש להגביל את חומת האש ואין לחשוף את הפורט לאינטרנט.
- מגבלת העלאה בצד השרת היא 10 MiB לקובץ מוצפן; מגבלת הודעת הפרוטוקול היא 16 MiB.
- טביעת אצבע שמתקבלת רק מהשרת אינה מוכיחה את זהות המשתמש. צריך להשוות אותה בדרך אמינה מחוץ לשרת.
- מרגע שה־Threshold הושג, הקובץ זמין רק למאשרים למשך 60 שניות ואז נמחק מהשרת. עותק שכבר הורד ופוענח יכול להישמר או להישלח הלאה.
- שרת זדוני יכול למנוע שירות או לשמור נתונים ישנים. ביטול אישור אינו מחיקה קריפטוגרפית.
- אם אובדים קובץ המפתח הפרטי המקומי או הסיסמה שלו, אי אפשר לפענח את ה־Shares של המשתמש.
- בהפעלה הראשונה על מסד נתונים מהגרסה הישנה, Shares מקוריים מועתקים לרשימת המשתמשים המורשים. אישורים קיימים אינם מועברים; כל המשתמשים מתחילים כלא מאושרים.
